A prompt tweak that improves one answer can quietly break fifty others. Teams that review prompt
changes by eyeballing a few outputs are flying blind.

## Treat prompts like code

If a change can alter behaviour in production, it deserves the same pipeline as code:

- A **golden dataset** of real inputs with expected properties.
- **Scorers** that check those properties automatically.
- A **threshold** that fails the build when quality drops.

## What a good scorer checks

Exact-match is rarely useful for generative output. Score properties instead: did the answer cite a
source, stay under a length budget, avoid PII, call the right tool?

```ts
expect(await score(run, [citesSource, noPII, maxTokens(400)])).toBeGreaterThan(0.95);
```

> A failing eval should feel exactly like a failing unit test: annoying, obvious and cheap to fix.
